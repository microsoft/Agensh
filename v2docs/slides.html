阶段一 · Foundation

让 Agent "用起来" 人类的协作平台

把 Git + 项目管理 这套大规模并行开发的成功范式，开放给 Agent

人类社会能做大规模并行开发，靠的是 Git + 项目管理 + 云平台 三件套。 第一步，是让 Agent 真的能在这套人类范式里干活 —— 不是 demo，是上岗。
  • 选定自建 Gitea 作为 agent 的协作中枢：issue / PR / review / merge / CI 一应俱全
  • 打通 Hermes Agent ↔ Gitea 双向通路，agent 拿到独立身份与 token，像人一样工作
  • 一键部署、零侵入上游：不 patch Hermes、不 patch Gitea，纯胶水层
  • 验收：单 repo 内 Issue → PR → Review → Merge 闭环跑通，agent 第一次"上岗"
意义：从"agent 单兵聊天"，迈向"agent 在企业级协作平台里工作"。
阶段二 · Protocol

把 MCP 做成 "反向协议"

统一事件输入 —— 上游兼容任意系统，下游兼容任意 Agent 框架

业界 MCP 都是 agent → 工具的正向调用。 我们做的是反向 MCP / 反向 ACP：让外部世界的事件，按统一协议反推给 agent。
  • 自建 omcgitea-router：把 Gitea 的协作事件（@mention / review / comment / merge…）精准投递给对应 agent
  • 上游兼容任意事件源 —— 今天是 Gitea，明天是 Jira / Azure DevOps / 飞书
  • 下游兼容任意 agent 框架 —— 今天是 Hermes，明天可以是别的
  • 工程上解决了大规模并行的硬问题：精准投递、批量合并、卡死自愈、不被广播淹没
意义：把"agent 接入企业系统"从一次性集成，升级为协议级标准。
阶段三 · Teamwork

从单兵作战 → 真正的团队开发

让 Agent 像企业团队一样有角色、有边界、有协作纪律

一个团队 = 一个 repo = N 个 agent。团队内部自组织分工，多 repo 即多团队并行。
  • 身份与权限：每个 agent 一个独立账号 + token + 角色（开发者 / 审查者 / 董事长）
  • 企业规约硬约束：禁直推 main、强制 review、approval whitelist —— 与人类同等纪律
  • 通知精准化：N 个 agent 在同一 repo 协作，每人只收"真正相关"的事件，不被噪音淹没
  • 工作流对齐人类团队：认领 issue → 开发 → PR → 互相 review → CI 绿 → merge → CD
意义：agent 不再是孤立调 LLM 的脚本，而是有纪律的团队成员。
未来 · Three Steps

步骤做什么产出

第三步 · 固化 把沉淀的 Skill / Memory 反哺训练，成为模型的先验能力 下一代具备团队协作本能的 LLM
核心资产 · 反向 MCP / ACP 协议
核心资产 · 企业级 Skill 库
核心资产 · 企业级 Memory 体系
我们做的不是又一个 agent demo —— 而是让 agent 学会"像企业一样协作"的基础设施。
